WLAN 架构与 PoE —— AP 的"领导们"和它的电

主课第 19 课讲了单台 AP 内部的软件栈（mac80211），这课拉远镜头看一群 AP 怎么被组织起来（架构三代史），以及一个容易被驱动工程师忽略的事实：企业 AP 全靠网线供电（PoE），供电问题会伪装成一切"稳定性异常"。

支点：架构演进 = 管理面不断搬家

本课支点 / Core Insight

三代架构（自治 AP → 控制器 → 云管理）变的不是 Wi-Fi 协议——802.11 该怎样还怎样——变的是三个平面放在哪：管理面（配置/监控）、控制面（关联/漫游/射频资源决策）、数据面（转发）。数据面放本地还是放中心，是性能的分叉点；控制面放哪，是排障的分叉点（出问题先问"这个决策是谁做的"）。

① 三代架构一张表

自治 AP（第 1 代）控制器 WLC（第 2 代）云管理（第 3 代）
管理面每台 AP 单独配（SSH（安全外壳）逐台）集中：控制器/网管统一下发集中：云平台（浏览器一处配全网）
控制面AP 自己上收控制器（关联/漫游/RF（射频）调优集中决策）云端协同 + AP 邻居间协商
数据面本地转发两种皆可：CAPWAP（无线接入点控制与配置协议）隧道回控制器集中转发，或本地桥接分布式转发本地转发为主（云只管管理面）
典型场景家用路由器、小办公室大企业园区、漫游敏感连锁店/分支多、IT（信息技术）人少
弱点规模一大管不动控制器贵、是单点断云=不能改配置（转发不受影响）

这个三平面框架和主课补充课 1的 Linux 栈分层是同一件事的不同切法——协议栈切的是"一台 AP 内部"，架构切的是"一群 AP 之间"。你写的 mac80211 驱动属于 AP 本地的实时部分，与架构代际正交（三代架构的 AP 里都跑着等价的实时 Wi-Fi 引擎）。

② 控制器时代的核心：CAPWAP 与 Split-MAC

CAPWAP (RFC 5415) — AP 与控制器之间的两条隧道 UDP 5246: 控制/管理隧道 DTLS(数据报传输层安全)强制加密 ← 配置下发/状态上报 UDP 5247: 数据隧道 DTLS 可选, 默认不加密 ← 集中转发时用户数据走这 Split-MAC(分离媒体访问控制) — 干活的分工线 留在 AP(实时性敏感, 毫秒级): Beacon(信标帧)/ACK(确认帧)/重传/加密快路径/速率控制执行 上收控制器(非实时, 需全局视角): 关联认证决策/漫游协调/RF 信道功率调优/策略下发 还有 Local-MAC 模式: AP 自己干几乎全部, 控制器只管配置

排障视角记一句话："决策谁做"——漫游出问题，在控制器架构里查控制器日志（决策在它），在云架构里查云的 RF 调优策略；"数据走哪"——集中转发下，AP 到控制器之间的网络故障会表现为"射频正常但全部断网"。

③ 专用基础设施巡礼（知道存在即可）

  • 无线网桥：楼与楼点对点（企课 3 的 WDS（无线分布式系统）应用形态）。
  • 室外 AP/.mesh AP：防水防雷防紫外，本质同室内 + 更高发射功率预算。
  • 远程办公室方案：AP 经 VPN（虚拟专用网络）回总部 + ZTP（Zero-Touch Provisioning，零接触配置）——设备通电联网后自动拉配置，分公司没有 IT 也能部署。
  • WNMS（WLAN 管理系统）：跨厂商/跨站点的统一网管（全网的"仪表盘"）。

④ PoE：AP 的命脉（稳定性排查必修）

企业 AP 几乎都是 PD（Powered Device，受电设备），由交换机或注入器供电。功率等级表（PSE（Power Sourcing Equipment，供电设备）端口最大输出）：

标准类型PSE 端口功率PD 实得（扣线损）俗称典型负载
802.3afType 115.4W（瓦）~12.95WPoE单频 AP、IP 电话
802.3atType 230W~25.5WPoE+双频 AP、球机
802.3btType 360W~51WPoE++高端 AP、视频会议终端
802.3btType 490W~71.3WPoE++照明、大屏

四个工程要点：

  • 供电设备两种形态：endspan（端接式，PoE 交换机，供电+交换一体）/ midspan（中跨式，注入器，挂在普通交换机和 PD 之间"补电"）。
  • 功率协商：PD 通过物理层分级 + LLDP（链路层发现协议）报上自己要几瓦（Class 0–8）——谎报的设备会被断电。
  • 预算（power budget）是总账：48 口交换机标 "PoE 预算 370W" ≠ 每口都能拿满——超预算时交换机按策略断谁的电，被断的 AP 表现为"随机重启/掉线"。
  • 线损真实存在：长网线/劣质线让 PD 实得功率缩水——AP 在高负载（发射功率拉满+多终端）时才掉电重启，是"负载相关重启"的经典特征。

对驱动工程师：架构落在你的固件里

对驱动重要 / For Driver Stack
  • 你写的固件是"实时半边"：Split-MAC（分离媒体访问控制）留在 AP 侧的那些功能（Beacon（信标帧）/ACK（确认帧）/重传/加密），就是主课 19 课 mac80211 那张 ops（操作回调表）——无论哪代架构，这部分是你的地盘。
  • 架构差异体现在第二进程：企业 AP 固件 = Wi-Fi 实时引擎 + CAPWAP/云管理 agent（代理程序）——后者出问题时 Wi-Fi 看起来"正常"，但配置改不动/漫游失效。
  • PoE 欠压的固件证据：随机复位先看复位原因寄存器/PMIC（电源管理芯片）日志——brownout（欠压复位）+ 复位时间与流量高峰重合 = 供电问题，不是软件 bug。别在协议栈里白找三天。

这课的钉子：三个平面 + 一张功率表

  1. 三代架构：自治（全在 AP）→ 控制器（管理+控制上收，CAPWAP UDP（用户数据报协议） 5246 控制/5247 数据）→ 云（管理上云、数据本地）；数据面放哪 = 性能分叉，控制面在哪 = 排障分叉
  2. Split-MAC（分离媒体访问控制）：实时（Beacon/ACK/重传/加密）留 AP，全局（关联/漫游/RF 调优）上收——你的固件就是实时那半边
  3. PoE 表：af 15.4W / at 30W / bt 60·90W（Type 1–4）；PSE（供电设备）endspan（端接式）/midspan（中跨式）；PD（受电设备）经 LLDP（链路层发现协议）报 Class（功率等级）0–8
  4. 两条排障铁律：预算是总账（端口×瓦数 vs 总预算）；负载相关重启先查供电（brownout 证据）再查软件
