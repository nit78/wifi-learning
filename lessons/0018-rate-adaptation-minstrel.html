速率自适应 —— 谁在决定用哪个 MCS

前面课里反复出现一句"信号差了就自动降到低 MCS"（第 13/15/16 课），但一直没回答：谁在选？怎么选？MCS 表有几十档（调制 × 码率 × 空间流），选高了丢包重传、选低了浪费吞吐——而且 Wi-Fi 没有基站指挥，发送端全靠自己猜。这课讲速率自适应 (Rate Adaptation / Rate Control)：从最朴素的 ARF 到 Linux 默认的 Minstrel-HT。

支点：没有反馈信道，只能试错

本课支点 / Core Insight

蜂窝网里基站拿 CSI 指挥手机用什么 MCS；Wi-Fi 里没有这个指挥——发送端能拿到的唯一可靠反馈是 ACK 到没到（或者 Block ACK 里哪些帧到了，第 12 课）。速率自适应的本质：用"成功/失败"的统计去猜当前信道能扛多高的速率。

两大门派：盲试派（拿丢包统计试出来，ARF/Minstrel）和信道测量派（直接看 SNR/CSI 查表，固件里常见）。前者不依赖硬件校准、对干扰鲁棒；后者反应快但 SNR↔MCS 映射因芯片而异、校准成本高。

① 先看选项：MCS 表到底多大

一条 11ac 链路的"菜单" (每条空间流): MCS0 BPSK 1/2 (最远也能收) ← SNR 要求最低 MCS1 QPSK 1/2 MCS2 QPSK 3/4 MCS3 16QAM 1/2 MCS4 16QAM 3/4 MCS5 64QAM 2/3 MCS6 64QAM 3/4 MCS7 64QAM 5/6 MCS8 256QAM 3/4 MCS9 256QAM 5/6 ← SNR 要求最高 × 空间流数 (1-8) × 带宽 (20/40/80/160) × 长短 GI → 组合数成百上千, 还要随信号实时换

11ax 的 MCS10/11（1024-QAM，第 15 课）再添两档。而且注意：速率是每个 STA 一份的——AP 对远处的 IoT 用 MCS2、对桌上的笔记本用 MCS9，同时进行（这才让 OFDMA/MU-MIMO 有意义）。

② 朴素算法：ARF / AARF

ARF (Auto Rate Fallback)，1997 年就有，规则简单到一行：

ARF: 连续 2 次失败 → 降一档, 并设"定时器" 定时器到 / 连续 10 次成功 → 试探升一档 ↑ 升档失败? 立刻降回来, 定时器翻倍 (下次更晚再试) 问题: 阈值全是拍脑袋的常数 —— 信道好的时候升得太慢, 信道抖的时候降得太晚, 静态信道里反复无谓试探

AARF (Adaptive ARF) 把"连续成功次数"改成自适应（试探失败就翻倍，成功后回到 10），减少无谓试探。它们是理解后续算法的基线：所有速率自适应都是在回答"什么时候降、什么时候升、升试探多少"这三个问题。

③ Minstrel：Linux 的正统答案

Minstrel（"吟游诗人"，取自 Minstrel in the Gallery）思路换成统计吞吐最大化：不看次数阈值，直接维护每个速率的成功率和期望吞吐：

对每个速率 r 维护 (EWMA 平滑): P(r) = 成功率 (指数加权滑动平均, 新样本权重高, 忘得快) T(r) = P(r) × 理论速率(r) = 期望吞吐 每 100ms 一个统计周期, 每帧按概率选: ~90% 用 max_tp: T(r) 最大的速率 (挑吞吐) ~10% 用 sample: 随机试别的速率(优先更高的) (保持探索) 退化时用 max_prob: P(r) 最高的稳妥速率 (重传/低信号用, 保成功) 本质: 多臂老虎机问题 —— 90% 利用(exploit) + 10% 探索(explore)

几个精妙细节：

  • 重传链：Minstrel 还维护一张 retry chain——首发用 max_tp，失败后逐级降速重试（最后兜底到 max_prob），重传本身就是一次免费的探测。
  • EWMA 忘得快：信道变了，旧统计迅速失效，几秒内换挡完成。
  • 吞吐而非成功率：一个 90% 成功的 MCS9 往往比 100% 成功的 MCS3 吞吐高（重传也划算）——ARF 类算法看不到这一点。

Minstrel-HT（11n 时代重写）是 Linux mac80211 至今的默认算法：把整个 MCS×流数×带宽 组成一个三维速率组统一统计，加了对 A-MPDU 的修正（见下节）。你在 /sys/kernel/debug/ieee80211/phy0/netdev:wlan0/stations/<mac>/rc_stats 能直接看到每档的成功率/吞吐/采样计数——调试速率问题的第一现场。

④ 聚合让统计变难

第 12 课的 A-MPDU 聚合和速率自适应互相纠缠，这是实践中的难点：

无聚合: 1 帧 → 1 ACK → 成功/失败, 一清二楚 有 A-MPDU: 64 帧打包 → 1 个 Block ACK: ┌ frame1 ✓ ─ frame2 ✓ ─ frame3 ✗ ─ frame4 ✓ ... ┐ Block ACK 位图: 1101...11 ← 一批 64 个样本一次拿回! 好处: 统计样本量暴增, 收敛快 麻烦1: "聚合成功率"≠"单帧成功率" —— 聚合本身要时间对齐, 速率高更容易坏 麻烦2: 速率决定聚合大小 (低速率帧耗时长, 聚太大占满 TXOP) 麻烦3: 11ax 以后统计粒度更细 (每 RU/每用户), 固件里叫 per-peer rate table

Minstrel-HT 的应对：统计单位改为聚合成功率（ampdu_success/ampdu_len），并按聚合长度修正期望吞吐。FullMAC 芯片的固件里，速率表和聚合长度通常是联合调优的一个状态机——这也是厂商固件真正下功夫的地方之一。

⑤ 另一派：SNR 查表（固件的私房菜）

芯片厂商固件常用信道测量派：收包时记 RSSI/SNR（甚至信道估计的 EVM），按出厂校准的 SNR→MCS 映射表直接选档，丢包统计只做兜底修正。

  • 优点：换挡快（一个包的 SNR 就够，不用等统计窗口）、上行选择更准（AP 对 STA 的链路质量在 AP 侧看包就知道）。
  • 缺点：SNR↔MCS 映射依赖射频链校准（每芯片每固件一份），干扰突发看不出（SNR 高但碰撞多），跨芯片不可比。
  • 11ax 之后趋势：协议本身在补反馈通道——上行触发帧里 AP 可以指定 STA 用什么参数（AP 主导的调度），等于把蜂窝那套"网络指挥"慢慢搬进 Wi-Fi。速率自适应正从"纯猜测"走向"半指挥"。

对驱动栈：rate control 落代码哪里

对驱动重要 / For Driver Stack

速率控制在 Linux 栈的落点：

  • SoftMAC：mac80211 的 RC API。算法实现为模块：rc80211_minstrel_ht.c（默认）、可插拔（ieee80211_rate_control_ops 注册）。驱动每发一帧回调 get_rate()，收 ACK 后上报 tx_status() 供统计。
  • FullMAC：速率表在固件。驱动/host 只下发初始速率限制（比如 11b-only 的 IoT 场景锁 MCS0），选择逻辑全在固件——固件工程师写的就是 per-peer 速率状态机 + 聚合联动 +（可能有的）SNR 查表。
  • 调试三板斧：① SoftMAC 看 rc_stats（每档成功率/吞吐/EWMA）；② iw dev wlan0 station dump 看 current rate/signal/重传统计；③ 抓包看实际 MCS 分布（Wireshark 的 Radiotap VHT/HE 字段）。"信号很好却跑在低 MCS"先看 rc_stats 是探测失败还是被限速。
  • 常见 bug：ACK 状态上报丢（tx_status 缺失 → 统计失真 → 卡在低档）；聚合长度和速率不联动（高速率聚太长 → 尾帧全坏）；多天线场景空间流升降抖动（1 流↔2 流来回切）；sample 比例设太高导致延迟敏感业务抖动。

自检：速率自适应吃透了吗

这课的钉子：90% 利用 + 10% 探索

学完这课，你脑子里应该有：

  1. 问题本质：无指挥反馈信道，只能拿 ACK 统计试错；盲试派（ARF→Minstrel）vs 测量派（SNR 查表）
  2. ARF/AARF：次数阈值升降档——所有算法的基线，三个问题：何时降、何时升、试探多少
  3. Minstrel：EWMA 成功率 + 期望吞吐最大化 + 90% 利用/10% 探索 + retry chain；Minstrel-HT 是 Linux 默认
  4. 聚合纠缠：Block ACK 位图样本暴增，但聚合成功率≠单帧成功率，速率与聚合长度要联动
  5. 趋势：11ax 起 AP 调度权增强，速率自适应从纯猜测走向半指挥

你现在能做的：

  • 看 rc_stats 判断"信号好但速率低"是探测失败、被限速还是统计失真
  • 解释为什么手机走远后吞吐是逐渐降而不是断崖（EWMA 平滑 + retry chain 兜底）
  • 理解 FullMAC 固件里 per-peer 速率状态机和聚合的联动设计
  • 用 station dump + 抓包的 MCS 分布验证速率自适应行为
